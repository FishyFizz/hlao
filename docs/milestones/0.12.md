# Milestone 0.12 — Provider session continuity

**Branch:** `dev`
**Baseline:** `8041b1a` (the last 0.11 commit)
**Source:** `FEATURE-REVIEW.md` P0-14 (resume) and R-19 (fork), plus the design discussion
recorded there as RF-01 through RF-08.

## Theme

The provider already keeps a durable transcript and ACP already exposes it. HLAO did not. A
session that evicted its bounded log or lost its supervisor could not be recovered, even though
a human using the same harness could resume the conversation and see its history. 0.12 closes
that gap with the primitives the adapter already advertises:

- `spawn --resume <providerSessionId>` reopens a provider session with ACP `session/load`.
- `spawn --fork <providerSessionId>` copies one with ACP `session/fork` and replays the copy.

The provider session id becomes the durable job handle. The HLAO id stays an alias for the
supervisor's lifetime. Nothing durable is added on the HLAO side: the provider owns the
transcript, and the spawner's own context carries the handle.

### Terminology

- **HLAO id** — the 6-character supervisor handle. It addresses a session inside one running
  supervisor and does not survive a restart.
- **Provider session id** — the adapter's conversation id (`SessionView.agentSessionId`). It is
  what the provider's own resume command accepts and what `spawn --resume` / `--fork` take.
- **Replay** — events rebuilt by ACP `session/load`, not observed live. They carry
  `EventView.replay: true` and are not new activity.

The interrupted turn is not replayed. Resuming restores history and context; the caller
re-issues the prompt, as a human would type "continue" after resuming.

## Decisions

### D1. Reopen, do not fork by default

`resumeSessionId` maps to `session/load`; `forkSessionId` maps to `session/fork`. They are
mutually exclusive. Resume is refused with `spawn_failed` when the adapter does not advertise
`loadSession`; fork is refused when it does not advertise `session/fork`. No silent fallback
to `session/new` under a resumed id.

### D2. The provider id is first-class

`SessionView.agentSessionId` is returned by every spawn, printed by human `spawn`, and shown by
`get` with a ready-to-run resume command. `SessionView.forkedFrom` records a fork's source.
ADR 0003's "diagnostics only" wording is amended; ADR 0011 records the new contract.

### D3. Fork replays its copy

ACP `session/fork` copies the conversation but sends no history. HLAO follows the fork with
`session/load` on the new id when the backend advertises it, so the client sees the same
history a human forking would see. `session.forked.historyLoaded` reports `false` when only
the copy (not the client view) could be produced.

### D4. Replay is marked, never counted as activity

Every event appended while `session/load` is in flight carries `replay: true`.
`session.resumed` and `session.forked` record the provider id and the replayed seq range.
Clients do not count replay as unread, and human `read` brackets it with
`— history restored from the provider —` / `— live —`.

### D5. In-process ownership is enforced; cross-crash ownership is not

A resume for a provider id already held by a live HLAO session returns that session
(`duplicate: true`) instead of opening a second adapter. Concurrent resumes are deduped in
flight. After a hard kill neither guard exists; the surviving hazard is RF-01.

### D6. Protocol 2.7 is additive

New capabilities `spawn.resume` and `spawn.fork`; new `SpawnParams.resumeSessionId` /
`forkSessionId`, `SpawnResult.resumed` / `forked`, `SessionView.forkedFrom`, and
`EventView.replay`; new event types `session.resumed` and `session.forked`. A 2.6 client
ignores all of it. Release version: 0.12.0.

## Wire changes — protocol 2.7 (additive)

```ts
// SpawnParams
resumeSessionId?: string;
forkSessionId?: string;

// SpawnResult
resumed?: boolean;
forked?: boolean;

// SessionView
forkedFrom?: string | null;

// EventView
replay?: true;
```

New event types: `session.resumed`, `session.forked`.
New capabilities: `spawn.resume`, `spawn.fork`.
`session.resumed` carries `{ agentSessionId, historyStartSeq, historyEndSeq, historyEvents }`.
`session.forked` adds `{ forkedFrom, historyLoaded }`.

## Out of scope

- Durable HLAO storage or a transcript authority. ADR 0002 stands; the provider is read, not
  copied into a new store.
- Live-session history loading (RF-03), provider enumeration/adoption (RF-04), cwd validation
  (RF-05), and the rest of RF-01 through RF-08.
- Replaying the interrupted turn. Callers re-issue prompts.
- Fork graphs in lineage. `parentId` remains the agent hierarchy.

## Acceptance

- A resumed session shows the provider's durable history with `replay: true`, and a human
  reading the transcript can see where restored history ends and live observation begins.
- A fork creates a new provider session, leaves the source untouched, and shows the copied
  history when the backend can load it.
- The provider id survives a supervisor restart in the spawner's own context and is sufficient
  to recover the job.
- Protocol 2.7 is additive; existing 2.6 clients and the full suite remain green.
