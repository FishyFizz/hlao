# Milestone 0.16 — Provider session discovery and adoption

**Branch:** `dev`
**Baseline:** `a57a754` (the 0.15 provider-permission commit)
**Source:** `FEATURE-REVIEW.md` RF-04 (provider session enumeration/adoption) and
RF-05 (resume cwd validation), plus the 2026-10-21 discussion of a persisted
provider-to-agent registry.
**Release:** 0.16.0 · wire protocol **3.1** (additive)
**ADR:** `docs/adr/0014-provider-session-discovery.md`

## Theme

The durable thing is the provider conversation, not an HLAO identity. After a
supervisor restart, or for a conversation created outside HLAO, a client could
not discover which provider sessions existed. The spawner had to remember the
provider id; a human could run `claude --resume` and pick from a list, but an
HLAO client could not.

0.16 closes that gap with the provider's own catalog:

- **Discover** provider sessions with `backends.sessions` / `hlao provider sessions`.
- **Adopt** one as a new HLAO session with `hlao adopt` or `spawn --resume`.
- **Keep no registry.** The provider owns the rows; HLAO only joins its live
  table to mark rows it currently drives.

The old HLAO id is not restored. Adoption creates a new HLAO attachment to the
same provider conversation, with a new handle, name, parent/root, and
environment.

## Terminology

- **Provider catalog** — the adapter's own `session/list` rows: provider session
  id, cwd, title, updatedAt. It is not an HLAO session list.
- **Provider-only row** — a catalog row with no live HLAO attachment. It may be
  an external session, or one this instance used before a restart.
- **Adoption** — loading a provider session with ACP `session/load` into a new
  HLAO session. `--fork` copies it with `session/fork` instead.
- **Registry** — a persisted HLAO-side map from provider session to agent.
  Deliberately not built.

## Decisions

### D1. Provider discovery is a read, not a store

`backends.sessions` calls ACP `session/list` on a short-lived adapter process.
It creates no HLAO session and no provider conversation, and writes no mapping.
The adapter process is killed on completion, client disconnect, or supervisor
shutdown. The live table remains the only instance-wide address space.

### D2. The wire returns provider rows plus a live join

`ProviderSessionsResult` carries the backend, the cwd filter (or null), the
adapter's agent name/version, provider rows, and the next cursor. Each
`ProviderSessionView` carries `sessionId`, `cwd`, `title`, `updatedAt`, the
adapter's `loadable`/`forkable` flags, and the live attachment when one exists
(`attached`, `hlaoSessionId`, `hlaoName`, `hlaoStatus`). A row without a live
attachment is labelled `provider-only`; clients must not present it as an HLAO
session.

### D3. Adoption is a client assembly, not a new server authority

`hlao adopt` is a CLI assembly over `backends.sessions` and `sessions.spawn`
with `resumeSessionId` (or `forkSessionId` with `--fork`). The supervisor gains
no adopt method and no stored mapping. A resumed provider session already live
in the instance is returned as a duplicate; no second adapter is opened. A fork
is a new provider session and is not deduped against the source.

### D4. The provider row supplies the cwd

When the catalog row is found, `adopt` uses its cwd. An explicit `--cwd` that
disagrees is refused rather than allowed to split the transcript (RF-05). If
the row is not found but `--cwd` is supplied, the caller's explicit assertion
is used; the provider load remains the authority on whether the id is valid.
If neither is available, the command refuses rather than guessing the process
cwd. `spawn --resume` remains the raw primitive: it trusts the caller's cwd,
and its help names the original-cwd requirement. The safe recovery/adoption
path is `hlao adopt`.

### D5. Reattach keeps the provider's mode

A resumed or forked session continues an existing conversation. The provider's
persisted mode is the default; `backends.<name>.defaultMode` applies only to a
new session. An explicit operator `--mode` still wins. This prevents a crash
recovery or an adoption from silently changing the conversation's permission
policy.

### D6. Capability-gated and honest about failure

The backend must advertise ACP `session/list`; otherwise `backends.sessions`
fails with a clear `bad_request`. A row is `loadable` only when the adapter
advertises `loadSession`; `adopt` refuses a non-loadable row before starting an
adapter. `--fork` similarly requires `session/fork`. A 3.0 client that does not
know the new capability simply never calls the method.

### D7. Protocol 3.1 is additive

New method `backends.sessions`, new capability `backends.sessions`, and the new
`ProviderSessionsParams` / `ProviderSessionView` / `ProviderSessionsResult`
shapes. No existing method, field, event, or error changes meaning. The mode
rule in D5 is a behavior correction for resume/fork only.

## Wire changes — protocol 3.1 (additive)

```ts
// method
"backends.sessions": ProviderSessionsParams -> ProviderSessionsResult

interface ProviderSessionsParams {
  backend: string;
  cwd?: string;      // absolute; omit for all cwds
  cursor?: string;
}

interface ProviderSessionView {
  sessionId: string; // the provider's id
  cwd: string;
  title: string | null;
  updatedAt: string | null;
  attached: boolean;
  hlaoSessionId: string | null;
  hlaoName: string | null;
  hlaoStatus: SessionStatus | null;
  loadable: boolean;
  forkable: boolean;
}

interface ProviderSessionsResult {
  backend: string;
  cwd: string | null; // the filter used, or null
  agentName: string | null;
  agentVersion: string | null;
  sessions: ProviderSessionView[];
  nextCursor: string | null;
}
```

New capability: `backends.sessions`. The wire minor moves to 3.1.

## Out of scope

- A persisted provider-to-agent registry or HLAO session index.
- Automatic job-tree recovery: recover one agent at a time; the root's own
  transcript or a user-space ledger carries child provider ids.
- Cross-instance duplicate detection or a lease. HLAO cannot see another
  client or another HLAO home driving the same provider session; `--fork` is
  the safe option when the source must stay untouched.
- RF-01 orphan reaping, RF-02 replay retention, RF-03 live-session history,
  RF-06 fork-without-load, RF-07 fork navigation, and RF-08 real-adapter
  fidelity. These remain provider-continuity hardening.

## Acceptance

- A provider-only session is visible with its id, cwd, title, and age, and is
  not presented as an HLAO session.
- A live HLAO session appears attached to its provider row by provider id.
- `hlao adopt` reopens the provider session, replays its history with
  `replay: true`, creates a new HLAO id/name/lineage, and uses the provider's
  cwd.
- A mismatched explicit cwd is refused before the adapter starts.
- A second adoption of the same provider id returns the live session as a
  duplicate; no second adapter is opened.
- A resumed older conversation keeps its provider mode even when the backend
  has a different `defaultMode`.
- Listing provider sessions creates no HLAO session and no provider
  conversation.
