# Milestone 0.11 — Provider-native state

**Branch:** `milestone/0.11-provider-state`
**Baseline:** HLAO 0.10 (`974c23c`, `milestone/0.10-truth-pass`)
**Source:** `FEATURE-REVIEW.md` R-10 through R-13 (residual), plus the dashboard protocol
evaluation in `docs/protocol-stability.md`.

## Theme

HLAO currently advertises only boolean config options to an ACP provider and projects the
provider's own work lossily: compaction is stored as `{}`, plan deltas render as a bare
`plan.update`, provider titles and agent identity never reach `SessionView`, and ACP's
inter-session messages become `raw`. 0.11 asks for the signals that describe **what the agent
is doing** and makes them first-class orchestration state.

This is the only remaining pass that changes what HLAO advertises to ACP providers. It adds no
scheduler, timer, store, or second authority. Every addition is an additive protocol 2.5 field,
event, or capability; a 2.4 client ignores it. Provider **subagent sessions** remain
deliberately out of scope: HLAO does not opt into that ACP surface.

The dashboard evaluation is a second consumer: it can start now against wire major 2, and 0.11
fills the optional provider-state slots it was told to leave (compaction, plan, title, agent
identity, messages) without a protocol break.

## Selection

### In scope

| Finding | Severity | Effort | What lands |
|---|---|---|---|
| R-10 context compaction | P1 | M | Advertise ACP compaction/notices; store and render compaction updates and summaries; add a context-pressure notice derived from usage |
| R-11 plan deltas and titles | P1 | M | Advertise experimental ACP plans; project plan updates/removals and the latest plan; store the provider title |
| R-12 inter-session messages and user chunks | P1 | M | First-class `session.message` events; render `user.message`; document the subagent-capability decision |
| R-13 residual provider identity | P2 | S | `agentName`/`agentVersion` in `SessionView`, `get`, and `list --wide` |

### Out of scope

- R-14's permission timeout/escalation mechanism, R-15's fleet-wide event stream, and the
  R-16..R-30 tail. 0.11 is provider state, not fleet observation or safety.
- N-08 enforcement, N-10 permission rules, N-11 bounds/budget.
- P0-14 resume; ACP `session/load` remains a separate contract.
- Provider subagent sessions (`clientCapabilities.subagents`), subagent cards, or a
  subagent-tree UI. The existing `subagent` event stays opaque and out of the default human
  view.
- A new `wait --until compaction` condition. A caller can already use
  `wait --until change --type compaction`; no new supervisor timer.
- Dashboard UI work. The dashboard is a client; 0.11 only guarantees the wire.

## Decisions

### D1. Advertise exactly what HLAO projects

HLAO's ACP `initialize` gains:

```ts
clientCapabilities: {
  session: {
    configOptions: { boolean: {} },
    compaction: {},       // ID-addressed compaction updates and summary chunks
    notices: {},          // live user-facing notices
  },
  plan: {},               // experimental plan_update/plan_removed
}
```

It does **not** advertise `clientCapabilities.subagents`. ACP gates
`session_message`/`session_message_chunk` on that experimental capability, so a compliant
adapter will not send them. HLAO still projects them defensively if a custom or non-compliant
adapter does, because turning them into `raw` is the worse failure. The deliberate omission is
documented in `contracts/protocol.md` and the README; it is a product boundary, not an
oversight.

The plan capability is advertised despite being marked experimental because plan deltas and
removals are the only way to keep a long-running dashboard's "what is next" view current. If a
provider sends a full `plan` replacement instead, HLAO handles that too.

HLAO's own capability list gains `session.compaction`, `session.notices`, `session.plan`,
`session.title`, `session.agent`, and `session.messages`. A client gates each view on the
capability it needs.

### D2. `SessionView` is the latest provider state; events are the history

`SessionView` gains optional fields (absent on a 2.4 supervisor):

```ts
compaction?: {
  id: string;
  status: "in_progress" | "completed" | "failed" | "cancelled" | string;
  summary: string | null;
  error: string | null;
  updatedAt: string;
} | null;

plan?: {
  planId: string;
  kind: "items" | "file" | "markdown";
  entries?: { content: string; priority: string; status: string }[];
  uri?: string;
  content?: string;
  updatedAt: string;
} | null;

title?: string | null;
agentName?: string | null;
agentVersion?: string | null;
```

- `compaction` is the latest compaction entity, with the accumulated summary text. A later
  `compactionId` replaces it; chunks append to its summary.
- `plan` is the latest plan. `items` plans carry entries; `file` and `markdown` plans carry
  their content so a client can render them without a provider-specific parser. A
  `plan_removed` clears the matching plan.
- `title` is the latest `session_info_update.title`; null clears it.
- `agentName`/`agentVersion` come from the ACP `initialize` `agentInfo`.

`list` uses `name ?? title ?? "—"` as its display label. Addressing is unchanged: a derived
title is never an addressable name. `get` adds title, agent/version, plan, and compaction to
the state block. `list --wide` adds one `AGENT` column (`name@version`); width work remains
R-21.

### D3. Provider events become structured and renderable

- **Compaction.** `compaction_update` and `compaction_summary_chunk` emit a `compaction` event
  with `{ compactionId, status?, summary?, text?, error?, updatedAt }`. A summary chunk carries
  `text`; an update may replace `summary` or clear it. The human renderer coalesces chunks by
  `compactionId` and prints `compaction › <status> · <summary>`; the bare `compaction` line is
  gone. The view's summary is the accumulated text.
- **Context pressure.** When a `usage_update` crosses 75% and then 90% of `usage.size`, the
  session emits a `notice` (severity `warning`) with the percentage and used/size. Thresholds
  are per-session, deduped, and reset below 70%. This is derived from provider events, not a
  timer; it does not stop or alter the turn.
- **Plans.** `plan_update` keeps the existing `update` field for compatibility and adds
  `planId`, `kind`, `entries`, `uri`, `content`, and `updatedAt`; `plan_removed` adds `planId`.
  The human renderer shows `plan › 2/5 done · current: …` or `plan › removed <id>` instead of a
  bare `plan.update`. A full `plan` event replaces the view.
- **Messages.** ACP `session_message`/`session_message_chunk` emit a new `session.message`
  event with `{ messageId, senderSessionId, recipientSessionId, content, chunk }`, where
  `content` is the extracted text. The human renderer coalesces by `messageId` and prints
  `from <sender> › <text>`. `user_message_chunk` (`user.message`) is rendered the same way
  instead of being ignored. Default JSON carries the fields; it no longer requires `--raw`.
- **Identity.** The `session.initialized` human line names the agent and version when the
  provider reported them. `get` shows them from the view.

### D4. Provider state is a projection, not authority

Compaction, plans, titles, messages, and agent identity are display state. They do not affect
addressing, policy, queues, waits, or lifecycle. A plan is not a scheduler; a title is not a
name; a compaction is not a memory store. No new supervisor timer or wait condition is added.
`subagent` updates remain opaque; 0.11 does not create provider child sessions or a second
lineage.

### D5. Protocol 2.5 is additive

New fields, event types, and capabilities only. The existing `plan.update` payload keeps
`update`; the new normalized fields sit beside it. A 2.4 client ignores unknown fields, event
types, and capabilities. A 2.5 client must check capabilities before using provider state, so
it can still talk to a 2.4 supervisor. Release version: 0.11.0.

## Wire changes — protocol 2.5 (additive)

```ts
// SessionView optional additions
compaction?: {
  id: string;
  status: string;
  summary: string | null;
  error: string | null;
  updatedAt: string;
} | null;
plan?: {
  planId: string;
  kind: "items" | "file" | "markdown";
  entries?: { content: string; priority: string; status: string }[];
  uri?: string;
  content?: string;
  updatedAt: string;
} | null;
title?: string | null;
agentName?: string | null;
agentVersion?: string | null;
```

```ts
// Event data
compaction: {
  compactionId: string;
  status?: string;
  summary?: string | null;
  text?: string;          // a summary chunk
  error?: string | null;
  updatedAt: string;
};

plan.update: {
  update?: unknown;       // preserved for 2.4 clients
  planId?: string;
  kind?: "items" | "file" | "markdown";
  entries?: { content: string; priority: string; status: string }[];
  uri?: string;
  content?: string;
  removed?: boolean;
  updatedAt: string;
};

session.message: {
  messageId: string;
  senderSessionId: string | null;
  recipientSessionId: string | null;
  content: string;        // extracted text
  chunk: boolean;
};
```

New event type: `session.message`.
New capabilities: `session.compaction`, `session.notices`, `session.plan`, `session.title`,
`session.agent`, `session.messages`.
No new methods, no new authority, no ACP `subagents` advertisement.

## Tests

- **Capabilities:** the signal adapter reports that it saw compaction, notices, and plan
  advertised, and no subagents.
- **Compaction:** in-progress, completed, failed, and chunked updates; view summary; human
  render; no bare `compaction` line; default JSON carries the fields.
- **Context pressure:** a usage update at 75% emits one warning, 90% emits one stronger
  warning, repeated updates do not duplicate, and a drop below 70% resets.
- **Plans:** full plan, item delta with `planId`, file and markdown plans, removal, view
  replacement/clear, and a compact human delta.
- **Titles:** provider title reaches `SessionView.title`, `list` uses it only as a fallback,
  `get` shows it, and addressing by name is unchanged.
- **Messages:** full `session_message`, chunked `session_message`, and `user_message_chunk`;
  coalesced human output; default JSON is not `raw`; no `subagents` capability is advertised.
- **Identity:** `agentName`/`agentVersion` in `get`, `list --wide`, and the initialized line.
- **Compatibility:** the existing 2.4 suite stays green; a 2.4 client that ignores the new
  fields still works; `hello` reports 2.5 and the six capabilities.
- **Full suite:** `npm run check` clean; unit, e2e, and acceptance suites green.

## Out of scope

- Provider subagent sessions (`subagents`), subagent cards, and a subagent tree.
- A scheduler, task store, DAG, durable transcript, or second authority.
- `wait --until compaction` and any new timer. Use `wait --until change --type compaction`.
- R-14's permission timeout, R-15's fleet event stream, R-16..R-30, N-08/N-10/N-11, P0-14.
- Dashboard UI. The dashboard is a client; 0.11 only guarantees the wire.

## Acceptance

- A compliant signal adapter receives the advertised ACP capabilities and its compaction,
  plans, notices, titles, messages, and identity appear in default JSON and human output as
  first-class state, never as bare `compaction`/`plan.update`/`raw` shells.
- `SessionView` exposes the latest provider state; `get` and `list --wide` use it, and a
  provider title is a display fallback only.
- Context pressure is a notice derived from usage events; there is no new supervisor timer or
  wait condition.
- `subagents` is not advertised; provider subagent sessions remain out of scope and are
  documented as such.
- Protocol 2.5 is additive; existing 2.4 clients and the full suite remain green.
